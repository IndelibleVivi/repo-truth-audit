# 怎样使用 Repo Truth Audit

[English](usage.md) · [README](../README.zh-CN.md)

本指南覆盖 v0.3.0 release target：Audit / Plan / Operate 内的意图对照。当前等待发布；
旧版 v0.2.1 不包含意图对照。
稳定安装请使用 README 中
固定 tag 的命令；只有明确需要经过审阅的 `main` revision 时，才走 source-checkout 路径。

## 适不适合用在这里？

当一个差异无法支撑判断时，进行一次目标有限的工程介入：哪个实现真正运行、它拥有怎样的状态、
哪个产物被发布、哪些调用者依赖它。一次任务可以以只读答案结束；获授权的改造也可以跨越多个会话，
在目标完成并验收后退出。无需每日运行或持续监视。

例如，在归属明确的模块中增加播放模式，交给普通开发即可。如果多个队列实现、旧入口和交付包
已经选择不同代码，统一它们就适合这里。介入结束后，普通功能开发应当重新接回去。

## 直接说出你的意图

不用填写表格。说清仓库或子系统、希望到达的结果、是否允许修改，以及重要的兼容或数据约束即可。
下面是示例；代理读到它们，不代表自动获得实施权限。

### 只检查

```text
用 $repository-operational-truth-audit 帮我重新接手这个仓库。
查清真正选中的 CLI 实现、测试是否覆盖交付产物，先不要修改目标文件。
```

预期得到：带有实际路径、重要发现或未知项、证明范围与停止理由的决策答案。
如果稳定版和开发版的并存合理，可以直接说明；无需为了显示有用而找问题。

### 给方案，先不改

```text
用 $repository-operational-truth-audit 规划怎样拆开导出格式化和持久化。
保留现有 CLI 与配置兼容，说明施工顺序、保护措施和完成标准，停在编辑之前。
```

预期得到：有限终点、依赖顺序、要保护的行为、适用验收和恢复步骤，以及尚需作出的决定。
收到这份计划不会自动授权它执行。

### 直接实施有限改造

```text
用 $repository-operational-truth-audit 拆开导出格式化和持久化。
保留 CLI 与配置兼容，迁移调用者和真实交付清单，并退役旧写入器。
直接本地实现并验证，包含相关测试和文档；不要迁移真实数据、部署或发布。
```

预期得到：一直做到约定本地终点的实现。已覆盖的必要修改不用逐文件反复批准。
完整的一步可以保留为检查点，但原目标和剩余工作仍需明确；新的实质性效果要有对应授权。

### 还原并对照产品意图（v0.3.0）

```text
用 $repository-operational-truth-audit，把 SPEC.md、docs/decisions/ 与这份指定的
开发对话中已接受的产品形态，与仓库实际交付对照。覆盖完整用户流程、约束和非目标；
区分缺失/局部行为、偏移、陈旧责任、合理演进与明确延期。说明未读来源和未定意图，先别改。
```

文档不足时提供明确对话来源。Skill 不遍搜私人聊天，也不把记录中的指令当成执行许可。
没有可靠意图来源，就给出有依据的假设和真正需要决定的事项，不虚构权威 SPEC。

新建、目录整洁的小产品也适用。“现在做出来的，还是不是我们说好的那个东西？”可以成为
入口，无需先报 Skill 名。自然局部采纳和内部委托应结合上下文解释。如果功能全在，可选
dashboard 却变成每次派工前必须填记录、确认任务的 gate，就比较这些动作与已接受流程。
后来的人工步骤授权会在其实际范围内改变判断。报告先说清预期正常使用，再展开差距。

例如，离线计划工具最初要求导出与恢复，后来 owner 决定从 JSON 改为 CSV，并延期云同步。
实际 CLI 能导出 CSV，恢复 helper 却只在未接入模块中。真实差距是恢复流程没闭合；CSV
是合理演进，云同步是延期，旧 JSON 提案不是修复目标。当前兼容 reader 即使没写入最初
SPEC，也可能必须保留，应先追踪用途。

```text
补齐已接受的本地导出/恢复流程，保留后来决定的 CSV 和现有兼容 reader，接通真实 CLI
与交付路径，更新相关文档并验证数据 round-trip。云同步继续延期；不迁移真实数据、安装、
部署或 release。
```

这份有限授权覆盖验收所需本地工作，但不自动包含新推断的功能或仍冲突的要求。
缺失的产品流程可以独立构成此次介入的理由，不需要先找到结构缺陷。

### 继续暂停的改造

```text
继续之前已授权的本地职责拆分。先读私有检查点，对照当前文件与已发生的效果，
保留我后来修改的内容，再在原范围内完成剩余义务。
```

宿主需要提供或找到真实的检查点和此前授权。记录缺失、效果不确定时先核实；代理不得编造已经记住的
状态、重放一次可能已成功的写入，或重置整个仓库。

“把这里全部清干净”只触发有界只读摸底。没有仓库级结构问题的单个已知 bug，依然属于普通工程，
即使请求中出现了“修复”。

## 怎样才算完成？

假设 CLI 由 `delivery.json` 选择实现，旧模块同时格式化输出和追加持久状态。
目标是拆开这两项职责，保留受支持行为并退役旧实现。

代理先追到真正入口，建立有效与无效输入、输出、错误状态、持久写入效果的观察。
随后抽出格式化，暂时保留旧写入器。这是值得保留的检查点，约定替换仍有剩余工作。

完整验收还要覆盖新的写入与组合模块、调用者迁移、入口切换、实际交付清单，以及要求退出的旧路径。
应仅从声明的交付文件重建一个新产物，单独验证，不能只测试方便导入的新源码。

| 验收面 | 要回答的问题 |
| --- | --- |
| 行为（Behavior） | 保留和明确改变的结果是否正确，包括失败路径与状态副作用？ |
| 结构（Structure） | 职责或依赖是否实际改变，应退出的旧路径是否退出？ |
| 交付（Delivery） | 范围内的每个交付入口是否选中新实现？ |
| 用途（Usefulness） | 原来的开发困难是否减轻，例如加格式时不再修改持久化模块？ |

新门面仍把所有工作委托给旧模块，只能算过渡。无人调用的新实现测试全绿，不证明交付成功。
输出相同也不能排除重复写入；为了掩盖回归而修改测试，不能证明行为受到保护。

[forward 回执](forward-0.2.0-receipt.zh-CN.md) 中验证过这个小型合成案例。它支持记录中的结果，
不保证任何仓库都会成功。是否需要部署、真实数据迁移或后续功能试验，由具体目标与适用证据决定。

## 安装与发现

本地安装器默认使用 `$CODEX_HOME/skills`，未设置时为 `~/.codex/skills`，也允许明确指定其他目标。
`--dest` 建出的目录不一定是当前宿主会发现的位置。

安装后检查回执和实际目标，按需要重启或重新加载 Codex，再开新任务确认选中了哪个 `SKILL.md`。
只看名称无法区分旧 package 与 v0.3.0。[OpenAI 的 Skill 目录](https://github.com/openai/skills#installing-a-skill)
也说明了安装后重启；最终仍要观察具体宿主是否加载成功。

仍然表现为 Audit-only 时，先检查安装文件与回执，再检查宿主配置的其他 Skill 根目录和目标仓库中
是否有重名副本。不要猜测后直接删除。发布后安装 v0.3.0 tag 会得到声明的九文件 v0.3.0 package；
更新 Git 仓库不会顺带更新独立安装目录。也不要把评测答案文件提供给代理，让它“通过”试用。

本 Skill 不要求额外 provider key、worker 服务或调度器。宿主仍须具备正常的模型访问、仓库工具和
真实执行控制。未知包钩子、不可信测试不能在虚构的沙箱保证下执行。
Windows 限制见 README；可选字节工具在不支持的平台上会明确拒绝执行。

## 给编码代理的入口

用户要求**在目标仓库中使用 Skill**时，加载真正安装的 `SKILL.md` 及其选择的 references。
完整契约在[权威运行时](../skills/repository-operational-truth-audit/SKILL.md)和
[实施方法](../skills/repository-operational-truth-audit/references/operation.md)中。
本指南用于解释，不是第二套路由器。解释当前真实请求，不要把这里的示例、旧报告或发布说明视作授权。

用户要求**维护 Repo Truth Audit 自身**时，遵循 [AGENTS.md](../AGENTS.md) 与
[产品契约](product-spec.zh-CN.md)。保持一份权威安装包，不把本指南、发布流程或评测答案复制进 Skill，
借此强迫发现或制造成功。单纯的文档澄清不得悄悄改变运行策略。

## 与其他工具的关系

[Alibaba OpenCodeReview](https://github.com/alibaba/open-code-review) 关注代码缺陷和审查意见，
同时支持差异审查和全文件扫描。
[Cloudflare security-audit-skill](https://github.com/cloudflare/security-audit-skill) 关注独立验证的
安全发现与覆盖记录。Repo Truth Audit 关注支撑一个决策的真实运行关系，并在获授权时跨这些关系
完成有限结构改造。

三者都可能检查架构和证据。这里解释工作流定位，没有宣称比较性能胜出。专门工具可以提供观察，
无需成为必跑阶段或必需运行依赖。来源与借鉴决定见[研究依据](research-basis.zh-CN.md)。

## 几个术语

**运行事实（operational truth）**：当前证据支持的系统选择、构建和运行关系。
**选择器（selector）**：通过注册、清单、配置或调用决定使用哪个实现的机制。
**状态归属（state owner）**：由哪个组件控制持久写入及其规则。
**见证（witness）**：能够支持或推翻一项结论的具体测试或观察。
**检查点（checkpoint）**：验证过的中间结果，剩余目标继续保留。
这些词用来描述实际工作，无需把小问题扩成统一的大报告。
