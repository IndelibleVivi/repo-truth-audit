[English](user-outcomes-study.md)

## 决策摘要

本轮最确定的进步是修复了一项评价器缺陷：八种暗中依赖导出机器的实现，都能通过旧 Cedar
修复验收；新的接收方检查拒绝全部八种，同时接受真正可移交的数据包。真实编译器、子进程、
跨进程消费者的观察进一步说明，这套判断怎样用于 JSON 交接之外的工程边界。

自然 Agent 实验承担另一项任务。四组配对比较不使用 RTA 与显式加载冻结候选，覆盖类型包
修复、数据包修复、合理的纯摘要工作流和部分迁移接续。独立结果与计量来源见
[实验回执](../evals/experiments/2026-11-user-outcomes/README.zh-CN.md)。这个小规模、
有意选样的实验不足以证明生产力提高。即使两边都能完成任务，更准确的判据仍是有价值的研究成果。

产品继续服务一次有明确决策或变更目标的介入。不增加仓库评分、模型运行器、强制审计阶段、
安装包中的评测依赖或自动宿主集成。

## 第一轮：先检查修复判据

### 缺陷

Cedar 的修订复核任务要求完整受影响记录、来源与修订关系、原始顺序和无重复结果。摘要晨会
只需要有序编号与文本。两种用途都把内容判断保留给专业读者。

旧 checker 在生产上下文中导出和查询。删除 store.json 后，仍有很多信息通道可用。本轮构造
八个可成功本地往返的方案：相对生产缓存、绝对源码目录缓存、数据包 sidecar、HOME 缓存、
临时目录缓存、包内绝对缓存指针、输入 sidecar 指针，以及源码有配置而 bundle 漏配后依赖缓存
回退的方案。旧修复判据全部放过。

这些是可执行反例。每个缓存方案先证明本地 export/read/affected 真能成功，再接受独立接收方
挑战，避免把语法错误或依赖缺失算成有效识别。

### 修复

现在在导出前准备接收方。生产和接收子进程使用不同的 HOME、profile、cache、临时目录；
导出后删除临时生产树与输入/输出目录，只把约定的数据包字节移交。源码接收方和声明 bundle
重建的接收方分别检查。

两个历史具有相同的可见摘要，却有不同的引用关系。同一个接收方按 0 → 1 → 0 顺序消费它们。
完整预期记录来自 evaluator 自己持有的输入；查询不得修改包或来源 store。这可以识别常量答案、
前次结果泄漏，以及源码与产物检查共享缓存的问题。

新判据拒绝旧版放过的全部八种方案。该阶段自挑战含十二个候选：接受两种合理编码，拒绝十个错误
候选。其中一个候选在源码层成功，只在声明产物的接收方失败，证明两层检查各有用途。

这里实现的是临时实验中的进程与资源分离；没有声称网络沙箱、恶意代码隔离、排除所有旁路，
也没有给所有产品增加离线义务。若已接受产品依赖保留的在线服务，就把服务计入接收方合同并验证。

### 信息充分性

一个简短的形式判断可以帮助决定：继续增加实现是否有可能挽救交接。令 s 为产品状态，h(s)
为接收者按约定能够收到或查询的全部信息，q(s) 为任务要求的答案。精确消费者函数 g 存在的
必要条件是：

`h(s1) = h(s2)  ⇒  q(s1) = q(s2)`。

否则 g 收到相同输入，却必须返回两个不同答案。反过来，在可达交接集合上，该条件允许按每个
等价类共同的答案定义 g。它说明信息是否足够，未证明实现效率、界面可用性或产品意图已被采纳。

Cedar 的相同摘要/不同引用历史，违反修订复核的条件，却满足摘要晨会的条件。同一种格式可以
胜任一个已接受用途，也可以无法完成另一个用途。给摘要产品增加引用机制，需要额外的用途依据。

## 第二轮：用真实消费者挑战局部成功

### python-dotenv：末端筛选不能纠正前段错误解释

旧源码 pin 为 `a00cb2eed0704cd6d2071b2004c37e95ccc86ee5`，上游修复为
`e0310e5bb3f2b701b11bbc007ca0c82c1bd56f38`。
[Issue](https://github.com/theskumar/python-dotenv/issues/697) 和
[已合并修复](https://github.com/theskumar/python-dotenv/pull/698) 提供任务与历史依据。

继承环境 base 为 environment，文件中 BASE=file、DERIVED=${BASE}/suffix 时，旧 CLI 在
no-override 下给子进程传入 environment 和 file/suffix。所有进程仍正常退出。现有 API
load_dotenv(override=False) 已经正确；所选前后 commit 的核心 main.py 字节相同。错误位于
实际 CLI 没有把覆盖策略传到插值阶段。

三个子进程观察足以区分方案：no-override 下继承非空值、继承空值，以及合法相反模式 override。

| 方案 | 非空 no-override | 空值 no-override | Override |
| --- | --- | --- | --- |
| 历史旧 CLI | 失败 | 失败 | 通过 |
| 上游修复 CLI | 通过 | 通过 | 通过 |
| 改未被实际使用的默认参数 | 失败 | 失败 | 通过 |
| 全局强制环境优先 | 通过 | 通过 | 失败 |
| 丢弃末端优先级筛选 | 失败 | 失败 | 通过 |
| README 增加错误成功声称 | 失败 | 失败 | 通过 |

加上已可用 API 控制，共十九个进程观察。矩阵不再具有预期区分力，或任何进程未能正常执行时，
probe 返回非零。工程含义很明确：末端筛选无法撤销前段依据错误策略产生的值；应跟踪选项经过
每个影响解释的阶段，并保留相反的合法模式。

### mitt：类型声明也是用户产品的一部分

Source main 为 `6b41670516ed8e8b738612f60491995470aa63b3`，3.0.1 tag 为
`b240473b5707857ba2c6a8e6d707c28d1e39da49`；所选 source、package metadata 和
README 在两者间相同。独立消费者使用真实 npm mitt@3.0.1 与 TypeScript 4.9.5。

带 `{foo: string}` 的类型化 emitter 无法编译 off('*')：通配 overload 要求 handler，运行时
却允许省略。现有运行测试及 JavaScript 调用都能通过，类型化应用仍无法进入能力。
公开说明和维护者的[通配语义澄清](https://github.com/developit/mitt/issues/150#issuecomment-1024417195)
支持有限修复；[旧的全监听器讨论](https://github.com/developit/mitt/issues/70#issuecomment-361379190)
帮助排除误删命名监听器的方案。

| 候选 | 源码类型检查 | 实际 package 类型检查 | 保留命名监听器 |
| --- | --- | --- | --- |
| 原 package | 无需作为判据 | 失败 | 是 |
| 源码 overload 已修，package 声明陈旧 | 通过 | 失败 | 是 |
| 实际交付声明修正 | 不作为决定层 | 通过 | 是 |
| 声明修正并调用 all.clear() | 不作为决定层 | 通过 | 否 |

编译器还必须继续拒绝无效事件名和错误 handler 类型。移除通配监听后的精确运行轨迹是：
之前的命名回调、之前的通配回调、之后的命名回调。无需重造 emitter 运行时。这也构成激活控制：
普通局部类型修复可以直接完成，无需自动引入完整 RTA 方法。

### CWR：保留真实修复，并明确用户结果的剩余边界

对照旧源码 `efc9613769960577f148c8e457a41f8c9e4ca234` 与当前修复
`18774c0628789b554db10e01189a367a21aad7fb`，使用同一真实 acpx@0.15.1 runtime 和

旧源码失败，当前源码通过。四项针对性测试覆盖遥测缺失/损坏、观察流结束及精确进程/请求身份。
成功回归特意保留 legacy last_seq 为零、旧 event-log 路径不存在。新活动合同有不同的状态 owner；
依据旧字段继续修复，会增加多余或错误工作。

[PR #12](https://github.com/IndelibleVivi/codex-worker-routing/pull/12) 已合并；
[Issue #11](https://github.com/IndelibleVivi/codex-worker-routing/issues/11) 在查看时仍 open/reopened。
Linux 生产方→活动→独立 CLI 已观察；报告者的 Windows/OpenCode 是否正确显示新字段尚未观察。
剩下的是这个精确的消费者采用检查，源码修复与完整 UI 验收应分别保留。

## 第三轮：候选冻结后加入新的 Go 案例

Viper 在冻结候选之后选取，Skill 未因此修改。它属于研究者按 issue 选择的迁移案例，没有
盲发现或自然 A/B 含义。真实 Go consumer 通过核对过的本地 module replacement 选择
`528f7416c4b56a4948673984b190bf8713f0c3c4`，使用 Go 1.27.4；源码始终干净。
未声称独立验证某个 Viper 发布包。

任务是将环境独有配置解码为 struct，修改值后重读。仅 AutomaticEnv 时，直接查询可见
alpha→beta，Unmarshal 却两次返回空字段且无 error。明确 BindEnv、登记 default key 和
ExperimentalBindStruct 三条路径都正确解码 alpha→beta。看似简便的 Set(key, Get(key))
首次有效，环境变化后仍为 alpha。空值控制分别保留默认 fallback 与显式允许空串的合法行为。

七个变体、十二次读取完全符合精确矩阵。上游 TestUnmarshalWithAutomaticEnv 也通过，但它
明确启用 experimental 模式。[汇总 issue](https://github.com/spf13/viper/issues/761)
解释懒查询与已知 key 枚举；[v1.18.2 发布记录](https://github.com/spf13/viper/releases)
解释为何 pointer 解码回归后默认关闭 struct binding。已有能力、默认任务不完整及兼容理由
应同时保留。一个单字段成功不足以支持全局开启实验功能或宣称环境支持整体损坏；固定应用
增加 BindEnv 可以直接作为普通工程完成。

离线 probe 先编译再运行，区分缺少编译器/cache 与消费者运行失败，并拒绝把输出/cache 写进
被观察仓库。六个仪器控制覆盖受保护路径、symlink、编译失败、真实已编译 panic 与非法 JSON。
PATH 上原有名为 go 的程序并非 Go 编译器，记录为 setup 控制；未修改用户 PATH 或系统安装。

## 自然 Agent 行为与介入成本

四组任务使用 fresh native session，每组任务和初始对象一致。候选组显式加载冻结 Skill，
控制组无 RTA；每任务每组只有一次，没有随机顺序，也没有稳定 release 处理组。精确后端模型
身份、token 使用、可归因任务时长、真实人工审阅时间均不可得。显式读取不证明宿主自动发现。

两边均通过四项独立任务。执行命令自报数为 mitt 15/15、Cedar 6/13、summary 8/10、接续 6/10。
没有成功率提升可报告，三组出现额外工具开销迹象；无法据此估计因果减速。简单已知修复仍不应
被强制路由到本 Skill。

受试者可以在任务范围内增加有意义的测试和本地操作文档。独立验收使用受保护的消费者检查，
不采用 Agent 自报成功。摘要审查的产品字节保护可以确定性核对，其范围判断仍需单独标明的
审阅。报告和命令数可以提示工作量，不能换算成人工分钟。

接续试验暴露出复用判据的适用性问题。TASK 要求 legacy.py 从所选 CLI 和 bundle 退出；
原 operation lab 则禁止文件存在，并扫描所有根级 Python 文件的文件 I/O。无 Skill 修复保留
转发兼容入口，增加 build/verify 工具，可以触发旧检查，却没有保留竞争的生产写入器。新的
trial verifier 保留原始拒绝记录，同时按 TASK 检查实际选择图与 bundle，没有改写旧实验更窄的合同。

scripts/compare_trials.py 接受离线回执，匹配对象、任务、宿主、设置和环境身份；保留失败、
阻塞和未判定样本，拒绝重复 arm 及不匹配对照，区分 Skill 已加载/可用未读，区分 observed、
proxy、unavailable。只有成对 observed 计量产生差值。证据定位是来源声明，不是认证证明；
工具不执行所引用的证据。

## 保留、修订与淘汰的方法

### 第四轮：独立审查新研究仪器

第一版接收方仍继承 XDG_DATA_HOME。只携摘要和随机缓存 key 的包，仍能从共享目录取回完整
记录，交错历史也无法阻止。APPDATA 有相同机制。两个反例先证明本地往返成功，并在修正前
被完整 gate 错误接受。现在每个生产/接收方的 XDG data/config/state/cache 和 Windows
application-data 根都分离。最终十四项挑战接受两种合法编码、拒绝十二种负例。任意环境变量、
绝对外部路径和网络通道仍不在可信 fixture 分离的保证范围。

review 还复现了未判定运行被显示为更快的可比结果、输出回执覆盖所观察 mitt 源码、dirty source
被归因于固定 commit、正确 Cedar 修复在 ASCII locale 失败。对应修正为：仅比较已判定且口径
匹配的结果、拒绝受保护输出路径、读取 Git pin 字节、明确 evaluator 与 fixture 子进程 UTF-8。
保留原始观察并复跑相同反例。集成中，dotenv archive 可移植改动曾短暂覆盖 variant 名称导致
KeyError，真实矩阵复跑捕获后已修正，最终交付前通过。

首次远端 PR CI 随后在 macOS、Python 3.10、Git 2.56 组合中暴露 fixture 初始化竞态，
其余三个 job 通过。fixture 基线 commit 启动的后台 maintenance，让变更前快照捕获了
`.git/objects/maintenance.lock`，随后该锁在变更后快照前消失，导致两个 Cedar 保留子检查失败。
真实 Git Trace2 探针复现了后台维护的启动，并验证了有限修正：两个 fixture 初始化器仅为各自的 commit
命令传入 `-c maintenance.auto=false -c gc.auto=0`。完整快照断言继续保留；未修改 local/global
Git 配置、产品 fixture 字节或权威 Skill，并增加了针对性回归。跨平台验收由修正提交的远端矩阵
提供；本地 Trace2 观察不能单独证明 macOS 验收通过。

这些修改作用于研究仪器，没有改变自然试验的冻结 treatment，也不能倒推为它带来的 Agent 成功。

### 方法决策

保留具体用户任务、实际消费者、一个症状见证和一个合法相邻用途。交接可能丢信息时，构造看上去
相同却要求不同答案的两个历史。先让假完成本地真正成功，再用接收方挑战。分别裁定语义变化、
旧要求、不可用环境和已接受的人工工作。

把笼统退役检查收敛到任务的实际 ownership 与 delivery 合同。文件名或 .open 搜索能找到候选，
不能单独裁定责任。将 checkpoint 与当前文件、所有者后续编辑对照。向所有者汇总一份决定与证据，
减少其自行拼接多份 worker 报告的工作。

当普通修复和一个消费者检查已经足够时，停止增加流程。不奖励报告长度、测试数量、Skill 术语、
删除行数或 Agent 数量。不要用重跑无关大套件替代缺失的精确宿主观察。未知人工成本继续留空。

## 研究依据与限制

[UTBoost](https://aclanthology.org/2025.acl-long.189/) 说明不充分测试可以接受错误补丁并改变
SWE-bench 排名，支持检查 outcome oracle，不证明本 Skill 的模型效果。
[OpenAI 编码评价审查](https://openai.com/index/separating-signal-from-noise-coding-evaluations/)
区分过严测试、任务欠定义、覆盖不足和误导 prompt；接续实例说明这些类别需要回到实际合同判断。
[SWE-Bench Pro V2](https://arxiv.org/abs/2610.24206v2) 使用独立重实现及干净环境复验；本轮借鉴
实现与裁定分离，未达到其规模。
[METR 2026 更新](https://metr.org/blog/2026-02-24-uplift-update/) 讨论开发者自选 AI 及并行 Agent
造成的选择偏差和时间计量困难。本轮缺失的人工时长保持缺失。

真实案例覆盖 Python、TypeScript 和 Node 进程集成，另有稍后记录的迁移案例；没有证明大型
monorepo、分布式迁移、真实生产数据或全部宿主的适用性。历史缺陷可能已为模型所知。指令限定
对象不是封闭沙箱。自报工具数是 proxy。后续自然运行先改进模型/宿主计量，再讨论因果效率。
